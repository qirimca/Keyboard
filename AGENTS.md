## Simulator & Device Testing Rules
- Every UI/keyboard change MUST be tested on **both iPad and iPhone** (iPadOS 26/27 + iOS 27).
- Check connected physical devices first (`xcrun devicectl list devices`, or `$IPAD_DEVICE_UDID` / `$IPHONE_DEVICE_UDID` in `.env.local`): **iPad Air 3rd generation** and **iPhone 15 Pro**.
- When testing on connected physical devices (via USB or Wi-Fi DeviceHub), notify the user in chat that physical device testing is starting and proceed immediately without blocking on confirmation.
- **Mandatory Parallel Execution Across Physical Devices & Simulator**: Connected physical devices and the already-booted simulator consume zero extra simulator disk space. Automated installations (`xcrun devicectl device install/process launch`) and test runs (`xcodebuild test-without-building` with separate `-resultBundlePath` paths) MUST ALWAYS be launched **in parallel simultaneously** across all connected physical devices and the active simulator — never sequentially one after another — so results from all devices are collected at the same time.
- If a physical device (e.g. **iPhone 15 Pro**) is offline/unavailable, you MUST test that form factor on an iOS 27 simulator (`xcrun simctl`):
  - Always monitor free disk space (`df -h /`) before and after every build/test run, and never run two `xcodebuild` commands simultaneously when free space is low.
  - If sufficient disk space is available, create/boot the missing approved simulator (**iPhone 15 Pro** / **iPhone 16 Pro** on iOS 27 or **iPad (A16)** on iPadOS 27) and test in parallel.
  - If disk space is tight (< 10 GB free), complete all tests, screenshots, and video capture on the active simulator first, delete that simulator (`xcrun simctl delete <udid>`) to reclaim space, and then create and test on the other form-factor simulator so both iPad and iPhone are thoroughly verified.
- Never pass `CODE_SIGNING_ALLOWED=NO` when building for Simulator (`xcodebuild`); Xcode's default ad-hoc signing with `.xcent` entitlements is required so `QTatar.app` and `Keyboard.appex` can share `UserDefaults(suiteName: "group.crh.key.keyboardplus")`.
- **Capacity-Aware Maximum Parallelism & Visual Proof**: Use the Mac's available CPU/RAM capacity to the maximum for parallel investigation, building, and testing while actively monitoring system load (`sysctl vm.loadavg`, `memory_pressure`) so concurrent tasks never conflict or freeze the machine. Every completed feature and fix MUST be verified and backed by visual evidence (screenshots or video recordings) in the final report.
- **Full-Power Builds, Safe-Maximum Resources & Disk Cleanup Guardrail**: Use the maximum resources that do NOT freeze the Mac (8 cores / 16 GB): start a build/test only when `sysctl vm.loadavg` < ~12, free memory (`memory_pressure`) > ~15% and `df -h /` free > 3 GB; **never run two `xcodebuild` at once** (parallel builds caused loadavg ≈ 688 and a system freeze on 2026-10-24). Agents MAY close/clean what they spawned and no longer need (stray simulators, hung `xcodebuild`/`swift-frontend`, `/tmp/qk_dd*`), but must never kill the user's Antigravity/Chrome sessions. Always clean `/tmp/qk_dd*` after installation so free disk never drops below `2.0 GB`.
- **Explicit Subagent Resource Budget & Strict `xcodebuild` Ownership**:
  - Every `invoke_subagent` / `send_message` prompt MUST explicitly pass the current hardware state (`8 cores / 16 GB RAM`, current `sysctl vm.loadavg`, `memory_pressure`, and `df -h /System/Volumes/Data` free space) and exact concurrency limits.
  - Read-only / investigation subagents are strictly forbidden from running ANY `xcodebuild` command (including `-showBuildSettings`, `-list`, or `-resolvePackageDependencies`), `swift build/test`, or `xcrun devicectl/simctl`, because even `xcodebuild -showBuildSettings` spawns `SWBBuildService` + `CoreDeviceService` (`DeviceHub`) + SwiftPM package resolution.
  - Only one designated agent/process at a time may invoke `xcodebuild` (`-jobs 4` max), and never in the same turn as multi-edit changes to large Swift files (`HomeView.swift`, `KeyboardViewController.swift`), so `language_server`, `SWBBuildService`, and `DeviceHub` never contend for RAM/CPU simultaneously.
  - Always check free disk space on `/System/Volumes/Data` (`df -h /System/Volumes/Data`, require $\ge 3\text{ GiB}$ free before any build, target $\ge 8\text{ GiB}$), and always pass `--exclude-dir="ШІ" --exclude-dir="Archive" --exclude-dir=".git" --exclude-dir=".build"` when running `grep -rn` or `find`.
- **Simulators Sequential, Physical Devices Parallel (do not deviate)**: Simulators are strictly sequential (one active simulator at a time, because each consumes disk), while physical devices (iPad Air 3rd generation, iPhone 15 Pro) take no disk space, so installs/tests on them and on the already-booted simulator stay **parallel** per the Mandatory Parallel Execution rule. Never silently downgrade this to fully sequential execution. If a device prompt needs a finger confirmation (trust/unlock/Allow), the agent MAY ask the user to confirm again when it actually appears.
- **Parallel Implementation + Continuous QA & Trace Subagent Pipeline**: Run a dedicated **Continuous QA Tester & Hang/Performance Trace Auditor** subagent in parallel alongside the **Implementation Engineer** subagent so completed sub-tasks are continuously benchmarked (`< 16.6 ms` frame budget, `< 100 ms` hang threshold, Unified Log / MetricKit / `.ips` audit) while implementation of subsequent tasks continues.
- **Subagent Continuity & Mandatory Timer Guardrails**: Never kill running subagents without a clear reason. If any subagent stops or must be replaced, spawn a continuation subagent with the exact `transcript.jsonl` paths of its predecessors so all unfinished work is resumed without loss. Always keep an active `schedule` timer whenever background tasks or subagents are running.
