## SQLite findings: actual current artifact, not the agent narrative

The uploaded local `QTatar/Demo/Keyboard/qırım_tatar.db` has Git blob SHA `a2fd0c57498f481c08ca03e16c8211be6d74ca62`, identical to the GitHub HEAD file.

- `PRAGMA integrity_check` => `ok`.
- `words` columns: **`word`, `freq`, `skeleton`**. The physical `lemma` column is **already absent** in this exact database, despite the v095 agent comment that it had been retained. No current production `lemma` query was found in `SuggestionsDataBaseManager.swift`.
- Counts: `words=215567`, `bigrams=63014`, `trigrams=12114`, `typo_corrections=101`. These are verified database counts, not the older tracker estimates.
- The swipe SQL using `substr(word,1,1)`, `substr(word,-1,1)`, and `freq>=2` uses `idx_words_first_last_freq` as a covering index in the local SQLite query plan.
- Prefix lookup using `word >= ... AND word < ... ORDER BY ...freq` uses the primary key and a temporary sort. This is not inherently a defect, but calls for on-device benchmarking if keypress latency grows. Generic `ORDER BY freq DESC` additionally incurs a temporary sort; avoid unmeasured index proliferation in v3.1.
- New `QTatar/Scripts/verify_keyboard_db.py` provides a **read-only**, automated schema, integrity, duplicate-entry and swipe-query smoke test. It deliberately does not enforce a physical `lemma` field.

## Platform decision for v3.1

- **iPhone / iPad:** same UIKit keyboard extension target; prioritise actual device testing across layouts, orientation, Full Access disabled, secure inputs and third-party-host restrictions.
- **macOS:** a native system-wide input method would be a **separate InputMethodKit** implementation, not merely an added destination for an iOS keyboard extension. A Mac-compatible host app does not imply a native macOS keyboard.
- **visionOS:** Apple says visionOS **does not load keyboard extensions** for compatible iOS/iPadOS apps. A standalone phrase/transliteration interface is plausible, but do not market this as a system keyboard.
- **watchOS:** Apple does not provide a system-wide third-party keyboard extension equivalent; the platform's text controls use system-provided input. A watch companion for phrases/transliteration would be a separate product.
- **Recommendation:** Keep macOS/visionOS/watchOS destinations out of v3.1. Extract shared, UI-independent transliteration/prediction core first, then design platform-native hosts. Avoid touching the SQLite schema just to satisfy a stale note.
