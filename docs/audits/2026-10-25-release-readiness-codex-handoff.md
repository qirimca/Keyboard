## Готовий промпт / execution contract для Codex

Ти — головний інженер і незалежний аудитор QırımKey. Ціль: **максимум реально перевірених, безпечних поліпшень** у межах доступного часу, ресурсів, прав і квот; пріоритет — робоча iOS/iPadOS клавіатура, приватність, App Review readiness, регресійні тести та якісні App Store assets. Не плутай кількість змін із прогресом. Не повторюй висновки попередніх агентів без доказів.

### 0. Середовище і provenance

1. Знайди **реальний робочий git checkout**, не припускай шлях з архівів; перевір `pwd`, `git status --porcelain=v1`, `git remote -v`, `git branch -vv`, `git rev-parse HEAD`, поточну Xcode версію та target/scheme. Не стирай чужі uncommitted зміни. Якщо checkout не збігається з release HEAD, задокументуй різницю й працюй в окремій гілці/worktree.
2. Знайди й **окремо розпакуй та прочитай обидва найновіші надані архіви** (локальний проєкт і архів розмов/налаштувань). Зафіксуй SHA-256 ZIP, список файлів, найновіші записи/повідомлення, дати та diff від GitHub; не видавай нечитані ZIP за перевірені. Захистися від path traversal під час розпакування. Ніяких секретів, .env, приватних повідомлень чи analytics у публічні коміти.
3. Прочитай `AGENTS.md`, потім **перевір його правила на суперечності з реальним станом машини**. Це інструкції, а не доказ успішних тестів. Якщо `AGENTS.md` конфліктує з безпекою даних, пріоритет — не втратити дані/роботу користувача.
4. Перевір, що саме зараз показує GitHub: branch, HEAD, open PR, issues/review comments, workflow logs, checks, discussions. Порівняй з цим документом, онови stale findings.

### 1. Ресурси, квоти й делегування

- Виміряй `sysctl -n hw.ncpu`, `sysctl -n hw.memsize`, `df -h /`, `memory_pressure`, `vm_stat`, `sysctl vm.loadavg`, `xcrun simctl list devices`, `xcrun devicectl list devices`. **Не приймай 8 CPU/16 GB з AGENTS.md без перевірки**. Перевір вільний диск і memory pressure до/після важких задач; зупиняй запуск нових робіт, якщо система перевантажена. Тримай запас для macOS/Xcode, не доводь диск до 2–3 GB. Не вбивай браузер, IDE, чужі процеси; не видаляй користувацькі симулятори/DerivedData без дозволу.
- **Лише один активний `xcodebuild`** одночасно; симулятори послідовно, якщо ресурси/диск обмежені. Фізичні підключені iPad/iPhone можна тестувати паралельно за умови відсутності конфліктів у signing, device prompts, DerivedData та result bundles. Перед фізичним тестом повідом користувача. Для кожного `xcodebuild` окремі `-derivedDataPath`/`-resultBundlePath` за потреби.
- Перевір реальний залишок квот у Codex `/status` або Settings → Usage; не вигадуй відсотки чи токени. Задачі ранжуй за impact/effort; фіксуй checkpoints, не запускай зайвих довгих циклів.
- Якщо Codex/оточення **дійсно підтримує** subagents та вибір моделей для них: головний агент — найсильніша доступна модель для архітектури, App Review ризику, security і фінального критичного review; сильна економніша модель для ізольованих patches/тестів; найдешевша доступна — для інвентаризації, локалізаційних diff, screenshot dimensions, CI triage. **Не припускай**, що головний агент уміє сам міняти модель або що субагентам можна задавати окрему модель: спочатку перевір можливості поточної сесії. Якщо недоступно — виконуй послідовно. Не множ субагентів, якщо вони конкурують за Mac, repo або квоту. Кожен субагент має окремий scope, критерій завершення та короткий доказовий handoff.

### 2. Черга виконання: швидкі виграші → критичні зміни

**A. Read-only baseline.** Збережи `git status`, commit/diff, Xcode/Swift version, device matrix, вільний диск, CI runs. Прочитай найновіші коментарі й заперечення щодо #10/#14/#15/#16/PR #13. Склади таблицю «порада → прийнято/частково/заперечено/відкладено → доказ → оцінка аргументу». Не оцінюй автора замість технічних аргументів.

**B. Невеликі безпечні виправлення.** Перевір актуальність README, release notes, скриптів, `AGENTS.md`, build settings, metadata, privacy text, локалізації, lint та GitHub Actions. Перевір `QTatar/Scripts/verify_keyboard_db.py` локально на фактичному `qırım_tatar.db` (read-only: `PRAGMA integrity_check`, `table_info`, `index_list`, `EXPLAIN QUERY PLAN`), не покладайся на старий `lemma` comment. Для кожного виправлення — маленький commit і тест.

**C. Release blockers.** Повний інвентар `NSClassFromString`, `NSSelectorFromString`, `perform`, `dlsym`, `method_getImplementation`, `unsafeBitCast`, приватних KVC, класів `UIKeyboardImpl`/`UIPeripheralHost`/`TIPreferencesController`. Врахуй **динамічно складені рядки**, які обходять поточний grep guard. Підготуй публічно-API-орієнтовану альтернативу для iPad floating/split і системних preferences; не видаляй приватні виклики «всліпу» до тестування поведінки. Потрібні негативні тести для guard і acceptance на реальному iPad. App Review 2.5.1 — ризик, не твердження про вже отриману відмову.

**D. Keyboard regressions.** Підтвердь на iPad Air 3 (якщо доступний), iPhone 15 Pro (якщо доступний) і відповідних симуляторах: docked/floating/split, pinch/callout/reopen, Shift/Caps, Crimean Tatar `İ/ı`, кирилична ФІВА/апостроф, swipe, suggestions, autocorrect-on-Space, quotes, punctuation, backspace undo, secure/URL/email/webSearch fields, Emoji, dark/light, onboarding, low memory, full access off, host app switch, clean install + upgrade. **Не маркуй PASS без `.xcresult`/логів/скріншотів і реального виконання.** Якщо тест флейковий, відокрем причину тесту від дефекту продукту.

**E. App Store Connect (тільки за фактичного авторизованого доступу).** Зістав версії/білди, TestFlight status, crash/termination metrics, downloads, acquisition/conversion, retention, devices, OS, geography, ratings/reviews, останні App Review messages та metadata з git і двома ZIP. Зберігай період, denominator, source і time zone кожної метрики; не роби висновків з малих вибірок. Приватну аналітику не публікуй у GitHub. Будь-які зміни сторінки, ціни, приватності, availability, submission, release або відправлення на review — **лише після явного погодження користувача**.

**F. App Store media.** Інвентаризуй усі наявні скріншоти/відео; перевір точні розміри, кольори, status bar, safe areas, мови, читабельність, правильний пристрій/OS і фактичний UI поточного білду. `01_latin_light_NEEDS_RETAKE_status_bar.png` — явно потребує повторного захоплення. Знімай **справжній UI** через XCUITest/`xcrun simctl io booted screenshot`/відеозапис після перевіреного білду; за потреби генеруй лише **позначені маркетингові ілюстрації**, не видавай AI-макет за скріншот програми. Не завантажуй у App Store Connect невалідовані assets. Віддай відтворюваний сценарій захоплення та список файлів/розмірів.

**G. GitHub best practices.** Аудит `CODEOWNERS`, issue/PR templates, workflow permissions, pinned action revisions, branch protections/rulesets, release tags, secrets exposure, binary assets, CI trigger coverage. Пропонуй мінімальні PR без force-push, без прямого commit у release/main, без merge. Для GitHub Actions failure перевір runner allocation, org/repo settings, spending limits, annotations; не називай це Swift compile error без job logs.

### 3. Критерії якості та фінальна здача

- Кожне твердження познач: **verified on GitHub / verified on Mac / verified on physical device / verified in ASC / archival claim / hypothesis / inaccessible**.
- Для змін: файл:рядок, commit SHA, diff, тест-команда, результат, артефакт `.xcresult`/PNG/відео, ризик, rollback. Дві незалежні перевірки тільки для критичних/спірних пунктів; не спалюй квоту на дублювання тривіальних тестів.
- Фінал українською: executive summary, два ZIP **окремо**, останні повідомлення й коментарі, GitHub diff, App Store analytics з точним періодом (або чесне «недоступно»), P0–P3 findings, виконані commits/PR, test matrix PASS/FAIL/BLOCKED, asset inventory, release gates, рекомендації щодо моделі/квоти, конкретний наступний крок.
- **Не роби реліз, не мерж, не змінюй production/App Store metadata і не публікуй приватні дані без окремого підтвердження.** Працюй у власній audit/worktree гілці, залишай зрозумілий handoff.
